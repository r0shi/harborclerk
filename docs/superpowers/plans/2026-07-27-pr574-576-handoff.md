- A "behavioural replacement" test that **could not fail**, replacing a crude

## 2. State of the two PRs

Both need `origin/main` merged first — the guards and #575 have landed since.

### #574 — `fix/mps-cache-growth`

Touches `embedder/` (app, reranker, new `gpu_cache.py`), compose, `.env.example`,
and three Swift files. Eight commits, five of them fixing review findings.

**What it does:** PyTorch's caching allocator never returns freed device blocks.
Normally self-limiting; not here, because input lengths vary by orders of
magnitude so the cache never reaches steady state. Measured on the Mac mini:
1.5 GB fresh → **40 GB after ~1.5 h of ingest** (peak 44 GB), with the machine
at 347 MB free, 15 GB compressor, 13 GB swap. Restarting the embedder returned
free memory to 11 GB.

It is **not a leak** — `current_allocated_memory` never moved off 594 MB and
`gc.collect()` changed nothing. Only `empty_cache()` returns it.

**Three interacting mechanisms, and the prior session got the interaction wrong
twice.** Understand all three together before touching any of them:

1. a **high-water mark** (4 GB) so single-query searches never pay
2. a **cooldown** so a drain that reclaimed nothing does not repeat
3. a **`finally`** so an OOM still drains before `embedder_client` retries

The first attempt released unconditionally, which drains the cache the next
query would reuse. The second attempt used a flat 5 s cooldown, which lands on
retry attempts 2–5 (0.25/0.75/1.75/3.75 s) and therefore **suppressed exactly
the drains the `finally` exists for**. It is currently gated on
*ineffectiveness* — a drain that worked does not start a cooldown. That is the
third design; treat it as unproven.

**Unaddressed review findings:**

- `/rerank` has **no worker-thread test** — the #553 invariant (release must not
  run on the event loop) is guarded for `/embed` only. Mutating the reranker
  call site to drain on the loop leaves all tests green.
- `_last_drain_at` is **check-then-set, not atomic**, and `/rerank` uses the
  default executor with no concurrency gate — so several threads can clear the
  check before any writes the timestamp. That is the concurrent case the
  cooldown was added for.
- The reranker's `finally` comment cites "the retry that follows"; there is no
  retry — `search_rerank.rerank_hits` catches once and degrades.
- `test_gpu_cache.py`'s fixture pops and re-imports the module, but `app.py`
  and `reranker.py` bound `release_gpu_cache` by `from … import` at import
  time, so a future test setting `ENABLED`/`CACHE_HIGH_WATER_MB` and driving
  `/embed` will silently have no effect.
- Neither compose service reserves a GPU, so `torch.cuda.is_available()` is
  False and the CUDA branch never runs on Docker. The compose comment reads as
  if the knob does something there.
- `AppSettings.gpuCacheHighWaterMB` has no UI affordance and no config.json
  migration — hand-editing only.

### #576 — `fix/imap-socket-leak-and-respawn`

Touches `mail/imap_client.py`, `watcher/mail_observer.py`,
`api/routes/mail.py`, and three test files. Three commits.

**What it does.** `IMAPConnection.logout()` sent LOGOUT only when `_logged_in`,
then dropped the client reference — which releases nothing, because aioimaplib
schedules `loop.create_connection(...)` in `IMAP4.__init__` and the transport is
owned by the event loop. It stays open until the server reaps it (~30 min on
Gmail). Harmless while a dead label task was never retried; the respawn added in
#569 turned it into ~6 concurrent sockets against a **15-connection
per-account** cap, so one sick label can lock out the healthy ones.

Closed at **two** call sites — the watcher's label task and
`POST /api/mail/accounts/{id}/test`. The second was found only in round 5; the
prior session fixed the first and missed the identical branch one file over.

Also: clamped the backoff exponent (`OverflowError`), stopped backoff state
outliving its label, and stopped logging deliberate exits as failures promising
a respawn that cannot happen.

**Unaddressed review findings — this branch has had no commits since its
review, so all of these are open:**

- The **production-common path is untested.** All three socket tests set
  `_logged_in = False`, and the API test uses `FakeIMAP`, which has neither
  `protocol` nor `_client_task`. Nothing exercises `logged_in = True` →
  `logout()` → `_close_transport`, which is the path taken on every watcher
  shutdown and every label cancel.
- `except BaseException` closes the transport but **skips the `_client_task`
  drain** — the asymmetry is benign today (reaching that line implies the task
  is already done) but the comment claims more than it delivers, and the branch
  is untested.
- The route-level test asserts only that `logout()` was *called*; because
  `FakeIMAP` lacks the attributes, it would pass if `logout()` regressed to a
  no-op. Only the observer test actually proves a socket closes.
- That test also sets `FakeIMAP._login_response` as class-level state and never
  resets it; `tests/api/` has no autouse reset (that fixture lives in
  `tests/mail/conftest.py`).
- The rename pin is weaker than it reads: the object is built with `__new__`, so
  the `hasattr` disjunct is always False and it is purely a string-in-`co_names`
  check. Catches a clean rename, not `transport` becoming a property.
- `test_reactivating_a_label_clears_its_backoff` covers the running-task path
  but does not assert `_spawned_at`.

## 3. Is this brittleness worth structural work?

**Not a full refactor.** The evidence is against it: the architecture produced
zero defects across five rounds. Storage abstraction, queue design, pipeline
idempotency, and the read-only IMAP layering all held. Restructuring would not
have prevented a single finding.

But three patterns are real, mechanically detectable, and worth bounded work.

### 3a. The same fix needed at N call sites, and the migration reaches N−1

Three independent instances:

| change | call sites | missed |
|---|---|---|
| error rendering | ~15 | `embedder_client.py` (written the same week) |
| connection cleanup on `AuthError` | 2 | `api/routes/mail.py` |
| `finally` on cache release | 2 | reranker had no test |

Every one was found by a reviewer, none by the author, and each took a full
round. **A `grep` for the old pattern before declaring a migration done would
have caught all three.**

*Suggested work, bounded:* make "did you grep for the second call site?" an
explicit item in the review policy in `AGENTS.md`. Consider whether the
error-rendering and connection-cleanup duplications can be collapsed behind a
single helper rather than repeated at each `except`.

### 3b. Tests that pass without exercising the change

Five rounds, same failure every time. The decisive question was always *revert
the changed line — does anything fail?* It caught, among others:

- three call-site edits in `embedder_client` where reverting any one was
  invisible
- a `finally` whose removal passed all 22 tests
- an entire `gpu_cache` function body replaced with `pass`, all 14 green
- a replacement test that could not fail, where the deleted original could

This is not a codebase property — it is an authoring habit. **Mutation-testing
is the only technique that caught it, and it caught it every single time.**

*Suggested work:* make mutation-verification the stated bar for anything
touching error handling, resource cleanup, or a `finally` — the three places
where vacuous tests concentrated. This is a process change, not code.

### 3c. Config that cannot be configured

Three knobs shipped unreachable because `ServiceManager.pythonEnvironment()`
builds a *closed* dict and Compose opts in one variable at a time. **This one is
now guarded** — `tests/test_env_vars_are_reachable.py` landed in #588 and caught
a fourth (`EMBED_NEEDS_PREFIX`, whose own comment said it existed "so the e5
rollback path keeps working") on its first run.

*Known limit, worth a decision:* the guard covers the ~17 **raw** `os.environ`
reads, not the ~59 pydantic `Settings` fields. Those reach the process by a
different route (`.env` on Compose, `config.json` on macOS), but `config.json`
is consulted for a handful of keys, not all of them. **Whether every `Settings`
field is actually settable on macOS is unanswered and is probably the larger
version of this bug.** That is a genuinely useful next investigation.

### 3d. Also worth knowing

- **`scripts/test_corpora/tests` is still uncollected** — 35 files, ~191 tests,
  the eval harness `AGENTS.md` names as how you prove retrieval hasn't
  regressed. It is a separate uv project needing its own CI job like `embedder`,
  and the harness is destructive, so the CI shape is a decision. Issue #587.
- **Test isolation is shaky.** Two independent flake observations:
  `test_chat_route_scope` failing then passing on re-run, and
  `test_observer_runs_initial_sync_for_active_label` failing 1 run in 4.
  Order-dependent tests erode the exact signal this work depends on.
- **`FakeIMAP` replaces the whole library**, which is precisely why the EXAMINE
  state bug survived to production — a fake that never had the bug cannot catch
  it. `tests/mail/test_imap_state_e2e.py` (a real socket) exists now as the
  counterweight; do not delete it as redundant.

## 4. Traps the prior session fell into

Stated plainly because they cost real time, and none are obvious in advance.

- **Do not trust a green suite on a change you just made.** Revert the line.
  Five rounds, five confirmations.
- **Do not chain lint and push in one command.** The prior session pushed past a
  red `ruff check` three times because the failure scrolled by.
- **Do not branch from another feature branch.** #588 accidentally stacked on
  #575 — `AGENTS.md` warns this once cost ~3,000 lines. It unstacked cleanly
  only because it was checked by hash.
- **A skipping test is worse than no test** — it reads as coverage. One written
  this week skipped because its fixture did not exist.
- **`ruff format` can silently break a string replacement.** Two edits this week
  appeared to apply and did not, because formatting had moved the target text.
  Verify the edit landed, don't assume.
- **Measure before naming a cause.** #553 was diagnosed as OOM by a prior
  session and was actually health-probe starvation — the embedder's `/health`
  went from 13.5 ms idle to 3,340 ms during a 64-text batch, against a 3 s
  supervisor probe. The memory pressure was real but was a *different* bug,
  found later.
