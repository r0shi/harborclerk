# Menubar Process Management — Tier B + C Refactor

**Status:** Design approved 2026-05-11. Pending plan-writing.

**Origin:** Audit memo `project_menubar_process_management_audit.md` (2026-05-11). Tier A fixes shipped in PR #341. This spec covers everything that was deferred from that PR.

## Goal

Eliminate the remaining ways the HarborClerkServer subprocess subsystem can leak children, race itself, or wedge during a normal model-switch or quit. The user-visible result: (a) menubar crashes no longer take Postgres down with them, (b) every force-kill reaches grandchildren (Tika's child JVMs, worker-spawned `pdftoppm`/`tesseract`), (c) there's always an escape hatch that doesn't require Terminal.

## Architecture

After the refactor:

```
launchd (PID 1)
├── HarborClerkServer                              ← user logged in, menubar app
│   ├── API                                        (child, own pgid)
│   ├── Embedder                                   (child, own pgid)
│   ├── llama-server                               (child, own pgid)
│   ├── Watcher                                    (child, own pgid)
│   ├── Worker io/cpu/llm (N children)             (each in own pgid)
│
└── launchd-managed agents in gui/$UID domain      ← installed by menubar at first launch
    ├── com.harborclerk.postgres
    │   └── postgres (postmaster) → backends       (launchd-managed pgid)
    └── com.harborclerk.tika
        └── java -jar tika-server.jar → child JVMs (launchd-managed pgid)
```

Three orthogonal subsystems change; everything else stays put.

### 1. Postgres + Tika move to launchd agents

The two heavyweight services become LaunchAgents in the user's `gui/$UID` domain. Plists at `~/Library/LaunchAgents/com.harborclerk.{postgres,tika}.plist`, installed/regenerated by the menubar at every startup (idempotent — only `bootout`+rewrite+`bootstrap` if contents differ from disk). Control model is **Y from the brainstorm**: `RunAtLoad=false` + `KeepAlive={SuccessfulExit:false}`. Menubar still owns the start/stop decision; launchd only contributes crash-survival (a Postgres or Tika crash gets auto-restarted by launchd, and a menubar crash leaves them running for the brief moment until menubar relaunches and re-attaches).

Other services (API, embedder, llama-server, watcher, workers) stay as menubar children because the survival benefit is small and the reconfig friction (model-switch flow, port changes) is high.

### 2. Every menubar child runs in its own process group

A new `Process.runAsProcessGroupLeader()` extension uses `posix_spawn` + `POSIX_SPAWN_SETPGROUP` (pgroup=0) so each spawned child becomes the leader of a fresh pgid. `killpg(pid, SIGKILL)` then reaches grandchildren. `forceKillEverything()` and `waitForExitWithDeadline()`'s SIGKILL escalation switch from `kill(pid)` to `killpg(pid)`. Normal SIGTERM-during-stop is unchanged; only force-kill needs the pgid form.

### 3. Auto-restart and shutdown coordinate

`HealthChecker` tracks every in-flight `attemptAutoRestart` Task in `taskHandles: [UUID: Task<Void, Never>]`. New `cancelInFlightRestarts()` method cancels them and awaits cancellation. `ServiceManager.stopAll()` calls this BEFORE marking services `.shutdownPending`, plus `configChangeTask?.cancel()` for the config-watcher path. Closes the race the audit found where a restart Task could pass the `.shutdownPending` gate and then call `start()` on a service the orchestrator already moved on from.

### 4. Force Stop All menu item

New `NSMenuItem` "Force Stop All" under the existing "Stop All". On click: NSAlert confirmation ("This will SIGKILL every Harbor Clerk subprocess. In-flight database transactions and document processing will be lost."), then `serviceManager.forceKillEverything()` plus `launchctl bootout` per launchd agent. The menubar **stays open** afterward — this differs from the 30-second deadline path which calls `exit(0)`. The semantic: "I want to break things and stay here to fix them," not "I want to quit and the normal path is wedged."

## Detailed design

### LaunchdAgent class

New `LaunchdAgent.swift`:

```swift
final class LaunchdAgent {
    let label: String                     // "com.harborclerk.postgres"
    let plistURL: URL                     // ~/Library/LaunchAgents/<label>.plist
    var domainTarget: String { "gui/\(getuid())" }

    /// Compare the in-memory plist content to what's on disk; if different,
    /// bootout, rewrite, bootstrap. No-op if already current.
    func ensureInstalled(plist: String) async throws

    /// `launchctl kickstart -k <domain>/<label>` — starts (or restarts) the
    /// service. `-k` ensures it's restarted if already running.
    func start() async throws

    /// `launchctl bootout <domain>/<label>` — stops the service.
    func stop() async throws

    /// `launchctl print <domain>/<label>` parsed for PID + state.
    /// Returns nil if not loaded.
    func status() async -> LaunchdStatus?

    /// `launchctl bootout` + delete plist file.
    func uninstall() async
}

enum LaunchdStatus {
    case loaded(pid: Int32?)   // pid nil if loaded-but-not-running
    case notLoaded
    case errored(reason: String)
}
```

Internally wraps `launchctl` invocations through a `LaunchctlClient` protocol so the high-level lifecycle logic is unit-testable against a fake. The real impl shells out via `Process.run`.

### Plist contents

Postgres plist (paths resolved at plist-generation time from `Bundle.main.resourceURL` and `AppSettings.shared`):

```xml
<dict>
  <key>Label</key>            <string>com.harborclerk.postgres</string>
  <key>Program</key>          <string>{bundle}/postgres/bin/postgres</string>
  <key>ProgramArguments</key> <array>
    <string>{bundle}/postgres/bin/postgres</string>
    <string>-D</string>       <string>{dataDir}</string>
    <string>-p</string>       <string>{port}</string>
    <string>-k</string>       <string>/tmp</string>
  </array>
  <key>EnvironmentVariables</key>  <dict>PGDATA, PATH, LD_LIBRARY_PATH, DYLD_LIBRARY_PATH, PGSHARE</dict>
  <key>RunAtLoad</key>        <false/>
  <key>KeepAlive</key>        <dict><key>SuccessfulExit</key><false/></dict>
  <key>StandardOutPath</key>  <string>{logsDir}/postgres-launchd.log</string>
  <key>StandardErrorPath</key><string>{logsDir}/postgres-launchd.log</string>
</dict>
```

`Program` is `postgres`, not `pg_ctl`. pg_ctl is a wrapper that runs `postgres` and exits — launchd would track the wrong PID and either restart-loop pg_ctl or orphan the postmaster.

Tika plist follows the same shape: `Program` is the bundled `java` binary, arguments include `-jar tika-server.jar --host 127.0.0.1 --port {port}`, env has `JAVA_HOME` and `PATH`.

### PostgresService / TikaService refactor

Both keep their `ManagedService` protocol surface (`start()`, `stop()`, `healthCheck()`, `state`). Internally they delegate:

```swift
final class PostgresService: ManagedService {
    private let agent = LaunchdAgent(label: "com.harborclerk.postgres", ...)

    func start() async throws {
        // existing first-run init dance (initdb, createDatabaseAndExtensions) stays
        // — those use Process directly and only run once per data dir
        try await ensureInitialized()
        try await agent.ensureInstalled(plist: buildPlist())
        try await agent.start()
    }

    func stop() async {
        await agent.stop()
    }

    func healthCheck() async -> Bool {
        // Unchanged — runs pg_isready
        ...
    }
}
```

`ServiceManager` sees the same protocol; no API changes there.

### Process.runAsProcessGroupLeader

In `ProcessExtensions.swift` (existing file from PR #341):

```swift
import Darwin

extension Process {
    /// Like Process.run() but launches the child as the leader of its own
    /// process group. Required for services whose children spawn further
    /// children (Tika's JVM child processes, Python workers spawning
    /// tesseract/pdftoppm/magick) — without this, killpg() can't reach
    /// grandchildren and force-kill leaks them to launchd.
    ///
    /// Implementation: posix_spawn with POSIX_SPAWN_SETPGROUP and pgroup=0
    /// so the child becomes its own pgid leader (pgid == pid).
    func runAsProcessGroupLeader() throws {
        // Resolve executableURL, arguments, environment, currentDirectoryURL,
        // standardOutput/standardError to file descriptors via
        // posix_spawn_file_actions.
        // Set spawn attributes:
        //   posix_spawnattr_setflags(&attrs, POSIX_SPAWN_SETPGROUP)
        //   posix_spawnattr_setpgroup(&attrs, 0)
        // Call posix_spawn, capture pid.
        // Mutate self's internal state to mirror what run() would have done
        // (so .isRunning, .processIdentifier, .waitUntilExit() all work).
    }
}
```

The implementation needs to faithfully mirror `Process.run`'s side effects on the receiver so existing call sites (`waitForExitWithDeadline`, `terminationHandler`, etc.) work unchanged. Risk: `Process` doesn't fully document its internal state machine — we'll need to validate by inspection + behavioural tests.

If reproducing `Process` state proves too fragile, fallback: provide a separate `SpawnedProcess` class that owns the pid, exposes `processIdentifier`, `terminate()`, `waitUntilExit()`, and a `terminationHandler`. Services that need process groups use `SpawnedProcess`; ones that don't keep `Process`. More code, less coupling.

### HealthChecker.cancelInFlightRestarts

```swift
final class HealthChecker {
    private var taskHandles: [UUID: Task<Void, Never>] = [:]   // NEW

    private func checkAll() async {
        // ... existing loop ...
        if count >= consecutiveFailuresBeforeError {
            let id = UUID()
            let task = Task { @MainActor in
                defer { self.taskHandles[id] = nil }
                await serviceManager.attemptAutoRestart(service)
            }
            taskHandles[id] = task
        }
    }

    func cancelInFlightRestarts() async {
        for (_, task) in taskHandles { task.cancel() }
        for (_, task) in taskHandles { _ = await task.value }
        taskHandles.removeAll()
    }
}
```

`ServiceManager.stopAll()` prepends:

```swift
stopConfigWatcher()
configChangeTask?.cancel()
await healthChecker?.cancelInFlightRestarts()
// ... rest of stopAll as it stands after PR #341 ...
```

### Force Stop All menu wiring

`AppDelegate.setupMenu()`:

```swift
let forceStopItem = NSMenuItem(title: "Force Stop All", action: #selector(forceStopAllServices), keyEquivalent: "")
forceStopItem.target = self
menu.insertItem(forceStopItem, at: stopItemIndex + 1)
```

```swift
@objc private func forceStopAllServices() {
    let alert = NSAlert()
    alert.messageText = "Force Stop All Services?"
    alert.informativeText = "This will SIGKILL every Harbor Clerk subprocess. In-flight database transactions and document processing will be lost."
    alert.alertStyle = .warning
    alert.addButton(withTitle: "Force Stop")
    alert.addButton(withTitle: "Cancel")
    guard alert.runModal() == .alertFirstButtonReturn else { return }

    Task {
        await serviceManager.forceKillEverything()
        // Bootout the launchd agents too — forceKillEverything handles
        // menubar children, but launchd-managed services need their
        // own teardown.
        await postgresService.stop()
        await tikaService.stop()
        serviceManager.notifyStateChanged()
    }
}
```

Menubar stays open after Force Stop completes — user can re-Start All when ready.

## Build order (four sub-PRs)

1. **PR-1 (small): Shutdown-aware HealthChecker.** Pure correctness improvement. Adds Task tracking + cancellation. No new files. Ships first to isolate teardown-race fixes from other changes.
2. **PR-2 (medium): Process groups via posix_spawn.** Adds the `Process` extension (or `SpawnedProcess` class if the extension proves fragile), migrates every menubar-child service to use it, updates `forceKillEverything` and `waitForExitWithDeadline` to use `killpg`. Tika still gets PG treatment even though it'll move to launchd in PR-4 — covers the inter-merge window.
3. **PR-3 (small): Force Stop All menu.** UI affordance + reuse `forceKillEverything()`. Trivial after PR-2.
4. **PR-4 (large): launchd migration for Postgres + Tika.** Adds `LaunchdAgent` and `LaunchctlClient`, refactors `PostgresService`/`TikaService` to delegate, plist generation, install/uninstall logic, status parsing. Most testing required; smoke-testing matrix covers first-run, upgrade, bundle-moved, plist-corrupted-on-disk, launchctl-failed.

## Risks

- **`Process.runAsProcessGroupLeader` fidelity to `Process.run`.** The extension needs to mirror `Process`'s internal state machine so `waitUntilExit`, `terminationHandler`, `isRunning`, `processIdentifier` all behave identically. If reproducing this proves too fragile, fall back to a separate `SpawnedProcess` class — more code surface, fewer hidden assumptions.
- **`launchctl` semantic drift across macOS versions.** macOS 14 is our floor (per `Settings.swift`); modern `bootstrap`/`bootout`/`kickstart` semantics stable since macOS 11. Low risk but worth a manual smoke test on each major-version boundary we support.
- **`LaunchAgent` uninstall residue when user trashes the app.** Plists in `~/Library/LaunchAgents/` outlive an app deletion. Harmless once nothing runs them, but cruft. **Out of scope for this refactor** — captured in `pr_followups.md` as "Tier C follow-on: uninstall.sh or 'Uninstall Services' menu item."
- **Testability of `launchctl` interactions.** Hard to integration-test from XCTest. Mitigation: `LaunchctlClient` protocol with a fake implementation for unit tests; real impl smoke-tested manually before merge of PR-4.
- **No fallback if launchctl fails.** Intentional. Surfaces a clear error rather than silently degrading to a different code path. Risk only matters in pathological OS states; we accept it for code simplicity.

## Out of scope

- **Embedder / llama-server / API / workers move to launchd.** Survival benefit per the brainstorm is too low to justify the reconfig friction. Revisit if model-switching ever becomes less central.
- **`SMAppService.agent`-based plist registration** (Apple's blessed framework for LaunchAgents from a regular app, macOS 13+). The plist must be embedded in the bundle at build time, but our bundle paths vary per install location — so the plist would need to point to a wrapper script. Adds an indirection layer we don't need given we're not sandboxed and can write to `~/Library/LaunchAgents/` directly.
- **Uninstall.sh / "Uninstall Services" menu item.** Tracked in `pr_followups.md`.
- **Architectural shift to RPC-based supervisor subprocess.** A separate `harbor-clerk-supervisor` process that owns all child lifecycles, with menubar talking to it via Unix socket. Considered briefly; rejected because launchd already solves the survival-of-supervisor problem for the two services that need it most, with less new code.

## Open implementation questions

- **Exact set of `EnvironmentVariables` per plist.** Pull from `Self.pythonEnvironment()` (ServiceManager.swift) for the parts that matter. Postgres needs `PGDATA`, `PATH`, `LD_LIBRARY_PATH`, `DYLD_LIBRARY_PATH`, `PGSHARE`. Tika needs `JAVA_HOME`, `PATH`. Settle during PR-4 implementation.
- **Health-check timing for launchd-managed services.** Currently `startService` polls `healthCheck()` every 1 s until ready or timeout. With launchd-managed Postgres, `pg_isready` is fine and unchanged. With launchd-managed Tika, the HTTP probe is unchanged. No behavior change expected.
- **Auto-restart-on-crash interaction.** Both menubar-side `HealthChecker.attemptAutoRestart` and launchd's `KeepAlive` will try to restart a crashed Postgres. With `KeepAlive={SuccessfulExit:false}`, launchd restarts only on non-zero exit; HealthChecker should NOT also restart launchd-managed services (it'd double-trigger). Add a flag to the service (`isLaunchdManaged: Bool`) to skip the menubar auto-restart path for them.
