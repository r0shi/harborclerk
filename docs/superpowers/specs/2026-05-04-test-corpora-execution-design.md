# Test Corpora Execution Design

**Date:** 2026-05-04
**Status:** Approved (sections 1–3 LGTM)
**Companion plan:** `docs/superpowers/plans/2026-05-04-test-corpora-execution.md` (pending)

## Goal

Validate that all 8 downloaded LLM models can complete Research and Ask flows end-to-end across three structurally-different corpora, then verify the two largest models (Qwen3.6 35B-A3B, Gemma 4 26B-A4B) reach Claude-level **search completeness** — same sources retrieved, same entities surfaced, same facts stated — when given Harbor Clerk's MCP tools.

This is a multi-hour operational sweep, not a CI test. The output is a per-(model, corpus, depth, question) result matrix plus a per-(top-2-model, corpus) parity report against a Claude baseline.

## Non-Goals

- **Overall answer-quality grading.** We measure search completeness, not prose quality, tone, or formatting fidelity.
- **Performance tuning per model.** We capture latency but don't iterate on `-np` or speculative-decoding settings during the sweep — that's a separate project.
- **Persistent test fixtures.** The DB is wiped between corpora and at the start of Phase 6. The user has confirmed nothing in the DB needs preservation.
- **Production CI integration.** This harness lives under `scripts/`, not `tests/`, and is invoked by hand. It is restartable but not automated.

## Architecture

A single Python script (`scripts/test_corpora/runner/sweep.py`) orchestrates six sequential phases. Each phase reads/writes a JSON state file so the sweep can be killed and resumed at any point. Per-question result artifacts are written atomically to a per-run results directory.

The harness runs on the user's Mac and talks to whichever Harbor Clerk instance is currently running — the macOS native server (the default) or a local Docker Compose stack (the user switches to Docker if the Mac client crashes mid-sweep, after quitting the Mac client). The API surface is the same in both cases.

The harness talks to Harbor Clerk over its REST API (the same surface the SPA uses):
- `POST /api/research/start` → poll `/api/research/{id}` until `state == "done"|"error"`
- `POST /api/chat` (SSE stream) for Ask flows
- `GET /api/docs`, `/api/stats` for corpus stats and citation resolution
- `POST /api/uploads/...` not used — we ingest via watched folders (the post-Stage-2 pattern)

The Claude baseline (Phase 1) and LLM-as-judge (Phase 5) talk to the Anthropic API directly. The baseline uses the same MCP tools Harbor Clerk exposes (`kb_search`, `kb_read_passages`, `kb_get_document`, etc.) so the comparison is apples-to-apples — Claude is being asked to search the same corpus the local models search.

## Tech Stack

- Python 3.12 (existing harbor-clerk venv reused; runner is a sibling top-level package under `scripts/`)
- `httpx` for Harbor Clerk REST + SSE
- `anthropic` Python SDK for baseline + judge
- `mcp` Python SDK to wire Harbor Clerk's MCP server into Claude's tool loop for the baseline
- `pyyaml` for question files
- `spacy` for entity extraction (already in the venv via Harbor Clerk's NER models)
- `tenacity` for retries
- No new dependencies required beyond what's already installed.

## Three Corpora

Per the existing `project_test_corpora_plan.md` brainstorm note. Recap:

### 1. CUAD — Contract Understanding Atticus Dataset

- **Source:** HuggingFace `theatticusproject/cuad-qa` or `theatticusproject/cuad`. License CC-BY 4.0.
- **Slice:** Sample 80 contracts spanning multiple industries. ~250 MB raw PDFs total; sample ~60 MB.
- **Why:** Real PDFs (mix of born-digital and scanned), long-form legal language, dense clause structure, **annotations give ground-truth answers** for retrieval evaluation.
- **Ground truth:** CUAD's clause annotations (governing law, termination, indemnification, etc.) are mapped to source contracts. Used as the gold standard for the Mechanical-only evaluation in Phase 4 *and* fed to Sonnet judge alongside Claude baseline in Phase 5.

### 2. Enron Email Subset

- **Source:** HuggingFace `corbt/enron-emails` or original CMU distribution. Public domain.
- **Slice:** ~3,000 emails, custodian-coherent — Skilling, Lay, Fastow, plus ~500 random others for noise. Total ~50 MB.
- **Why:** `.eml` format exercises Tika's email path; threaded conversational content; rich real-world entities; small-business archetype mapped to "mid-sized company before collapse."
- **Ground truth:** None inherent. Claude baseline (Phase 1) is the gold standard.

### 3. Synthetic Bilingual Small Business

- **Source:** Generated by Claude (Sonnet 4.6) via the `corpora/synthetic.py` script.
- **Slice:** ~300 documents for fictional company "Marbledock & Associates":
  - 60 invoices (English)
  - 40 employee onboarding letters (mixed EN/FR)
  - 30 board meeting minutes (mostly EN, some FR per a defined "language policy")
  - 30 vendor contracts (English)
  - 30 internal memos (mixed EN/FR)
  - 30 policy docs (mixed EN/FR)
  - 20 marketing briefs (English)
  - 20 employee handbooks (one per "year" bilingual)
  - 20 quarterly reports (mostly EN)
  - 20 deliberately-scanned PDFs (a subset of the above re-rendered at 150 DPI with slight noise/rotation to force OCR)
- **Why:** Maximum control. We author ground-truth answers alongside generation. Tests bilingual FTS (`fts_en` + `fts_fr` columns), French NER (`fr_core_news_sm`), OCR conditional path, mixed-format ingestion.
- **Ground truth:** Authored at generation time. Each document gets a JSON sidecar with structured facts (price, dates, signatories, parties). Question authoring references those sidecars.

### Acquisition outputs

Each corpus's `acquire()` returns:

```python
{
  "corpus_id": "cuad" | "enron" | "synthetic",
  "ingest_dir": Path,           # what to point a watched folder at
  "doc_count": int,
  "total_size_bytes": int,
  "ground_truth": dict | None,  # optional structured facts
  "license": str,
  "notes": str,
}
```

The harness wipes the DB, points a watched folder at `ingest_dir`, and waits for `pipeline.queued + pipeline.running == 0` via `/api/stats` before declaring the corpus ingested.

## Six Phases

| Phase | Goal | Models | Corpora | Depth | Time budget per question |
| --- | --- | --- | --- | --- | --- |
| 0. Acquire | Download CUAD, Enron subset; generate synthetic bilingual; capture per-corpus stats | — | all 3 | — | — |
| 1. Baseline | Generate Claude baseline answers to all questions for all 3 corpora | Claude (external, via MCP from outside Harbor Clerk) | all 3 | n/a | n/a |
| 2. Smoke | Iterate until **one** large model completes one corpus end-to-end at standard/30m. Bug-fix logging, code paths, etc. | 1 of {Qwen3.6 35B, Gemma 26B} | 1 corpus (CUAD) | standard | 30m |
| 3. Depth | Same model, all three depths {light, standard, thorough} on same corpus | same | same | all 3 | 30m |
| 4. Models | Each remaining model × each corpus × standard/30m, completion-only | all 8 | all 3 | standard | 30m |
| 5. Parity | Run questions through Qwen3.6 35B + Gemma 26B against all 3 corpora, compare to Claude baseline (mechanical + Sonnet 4.6 judge) | top 2 | all 3 | standard | 30m |
| 6. Unified | Drop DB, ingest all 3 corpora into one DB, run cross-domain question subset through top 2 | top 2 | unified | standard | 30m |

Phase order rationale:
- **0 → 1** — both can run in parallel once Phase 0 produces ingest dirs; Phase 1 doesn't need the local models.
- **2 → 3** — get one model green at 30m before exploring the depth axis.
- **3 → 4** — only fan out to all 8 models once we know the largest model works at all depths.
- **4 → 5** — only run the expensive parity comparison once all models complete.
- **5 → 6** — unified pass requires DB reset, so it's last.

Phases 2–4 are **completion-gating**: success criterion is "model returns *something* with citations." Phase 5 is where we measure quality.

## Phase 0 detail — corpus acquisition

Each `corpora/<id>.py` module exposes `acquire(workdir: Path) -> CorpusManifest`. Idempotent: if the corpus is already on disk, returns immediately.

- `cuad.py`: downloads CUAD release tarball, extracts, samples 80 contracts deterministically (sorted by filename + first 80) for reproducibility.
- `enron.py`: downloads the corbt/enron-emails dataset, filters to Skilling/Lay/Fastow custodians + 500 random with seed=42.
- `synthetic.py`: invokes Sonnet 4.6 with templated prompts to generate each document type. Saves doc + JSON ground-truth sidecar. Re-renders 20 randomly chosen documents at 150 DPI through pypdfium2 with noise/rotation for OCR forcing. Idempotent via content-addressed filenames.

## Phase 1 detail — Claude baseline

`runner/claude_baseline.py` connects to the local Harbor Clerk MCP server via `stdio` transport (or HTTP — whichever is simpler). It then asks Claude (Sonnet 4.6) each question with the MCP tools available. The prompt mirrors what an LLM client would send: "You have access to a knowledge base via these tools. Answer the user's question using only the corpus."

Output: one JSON file per (corpus, question_id) with:
```json
{
  "question_id": "cuad-research-1",
  "question": "Compare termination notice periods across the corpus.",
  "answer": "30/60/90 day windows dominate; 7 contracts use termination-for-convenience...",
  "cited_doc_ids": ["...", "..."],
  "named_entities": ["California", "Delaware", ...],
  "tool_calls": [...],
  "elapsed_seconds": 87.4,
  "model": "claude-sonnet-4-6",
  "timestamp": "2026-05-04T...",
}
```

This is the gold standard for Phases 5 and 6.

## Question Framework

**Per corpus: 6 research + 10 ask logical questions.**

Two of the synthetic-corpus questions are cross-language pairs (one research, one ask), each running as two completions (EN + FR). So the **completion** counts are:

| Corpus | Logical Q | Completions |
| --- | --- | --- |
| CUAD | 16 | 16 |
| Enron | 16 | 16 |
| Synthetic | 16 | **18** (one extra for each of the two cross-lang pairs) |
| **Total per model** | 48 | **50** |

Phase 4 sweep = 8 models × 50 completions = **400** completions. Phase 5 judge calls = 50 questions × 2 models = **100** judge calls. (Cross-language variants are judged as two separate completions against the same baseline; the EN baseline is used for both unless a French baseline is generated separately, see Bilingual Scope.)

Question files live at `scripts/test_corpora/questions/<corpus>.yaml`. Schema:

```yaml
research:
  - id: cuad-research-1
    text: "Compare termination notice periods across the corpus."
    ground_truth_doc_ids: []  # optional, populated for CUAD/synthetic where known
    notes: ""
ask:
  - id: cuad-ask-1
    text: "What is the governing law of [Acme Master Service Agreement]?"
    ground_truth_answer: "California"  # optional
    notes: ""
```

The user reviews the question files in the PR; questions can be swapped at any time and a `--rerun questions=cuad` flag reruns only the matching ones.

## Comparison Framework

### Mechanical metrics (every completion)

Computed and logged for every (model, corpus, question, depth) tuple:

- **`citation_overlap`** — `|sources ∩ baseline_sources| / |baseline_sources|` at the **doc_id** level. Range [0, 1]. Higher = better. Doc-id, not chunk — chunk overlap is too noisy.
- **`citation_extra`** — `|sources \ baseline_sources|`. Counts extra sources not in baseline. Not necessarily bad (model found something Claude missed) but tracked.
- **`entity_overlap`** — Recall of named entities in the answer text vs the baseline answer text, extracted via spaCy `en_core_web_sm` and `fr_core_news_sm`. `|entities ∩ baseline_entities| / |baseline_entities|`. Range [0, 1].
- **`latency_seconds`** — wall clock from request to final response.
- **`prompt_tokens`** / **`completion_tokens`** — if exposed by llama-server's `/timings`.
- **`tool_call_count`** — how many `kb_*` calls the model made.

Stored in `results/<run_id>/metrics.csv`, one row per completion.

### LLM-as-judge (Phase 5 only)

For each `(question, baseline_answer, model_answer)` triple in Phase 5, send to **Sonnet 4.6** via the Anthropic API with this rubric:

```
You are evaluating whether a local LLM's answer reaches the same factual
ground as a Claude baseline answer to the same question.

Question: {question}

Claude baseline answer:
{baseline}

Local model answer:
{model_answer}

Score these dimensions (0–5 each):
- claim_recall: how many factual claims from the baseline appear in the
  model answer (verbatim or paraphrased)?
- claim_precision: are the claims in the model answer supported by the
  baseline (or harmless additions), or are they contradictions?
- entity_recall: does the model answer surface the same named entities
  (people, places, organizations, dates, dollar amounts)?
- completeness: overall coverage of the baseline's territory.

Return JSON only:
{
  "claim_recall": int,
  "claim_precision": int,
  "entity_recall": int,
  "completeness": int,
  "missing_facts": ["..."],   // facts in baseline absent from model
  "extra_facts": ["..."],     // facts in model absent from baseline
  "contradictions": ["..."],  // facts in model that contradict baseline
  "verdict": "pass" | "marginal" | "fail"
}
```

Phase 5 = 50 completions × 2 models = 100 judge calls. Sonnet 4.6 inputs are small (~5–10 K tokens each) so total spend is on the order of $1–$2.

### Module responsibilities

- `corpora/<id>.py` — single function `acquire(workdir) -> CorpusManifest`. Idempotent. Knows nothing about the runner.
- `runner/client.py` — REST client for Harbor Clerk. Methods: `start_research(question, model, depth, time_limit)`, `poll_research(task_id)`, `stream_ask(question, model)`, `wait_for_quiet_pipeline()`, `wipe_db_and_ingest(corpus_dir)`.
- `runner/claude_baseline.py` — runs Sonnet 4.6 with the Harbor Clerk MCP server attached as a tool source. Emits per-question baseline JSON.
- `runner/judge.py` — sends `(question, baseline, model_answer)` to Sonnet 4.6 with the rubric. Returns the structured JSON verdict.
- `runner/metrics.py` — pure functions: `citation_overlap(baseline, model)`, `entity_overlap(baseline_text, model_text, lang)`. No I/O.
- `runner/state.py` — load/save state. Atomic write via temp-file + rename. Lock file at `<run_id>/state.lock` to prevent two runners.
- `runner/sampler.py` — counts completions and prints sample cards every 5th completion plus phase-boundary tables.
- `runner/sweep.py` — entrypoint. Reads state, schedules the next pending unit, executes it, updates state, repeats.

## Restartability

Three layers, all idempotent.

### 1. Per-completion idempotency

State file keys every unit of work as `(phase, corpus, model, question_id, depth)`. State values:

| status | meaning | re-run on `--resume`? |
| --- | --- | --- |
| `pending` | not started | yes |
| `in_progress` | runner is currently working on it | yes (after stale-recovery) |
| `done` | response file written, metrics recorded | no |
| `degraded` | response written but model returned no citations / empty answer | no |
| `error` | API error / timeout / OOM after 3 retries | no (but `--rerun` clears it) |
| `failed` | hard failure (model not loadable, etc.) | no (but `--rerun` clears it) |
| `skipped` | user explicitly skipped via `--skip` | no |
| `blocked` | system-level error (DB down, llama-server crashed) | yes (after manual fix) |

On startup the runner reads `state.json` and skips anything not `pending` / `in_progress` / `blocked`. Each completion writes its result file *first*, then atomically updates state.

### 2. Crash-recovery

Active work has `status: "in_progress"` with a heartbeat timestamp updated every 30s. On startup, any `in_progress` row older than `2 × time_budget` reverts to `pending`. No partial response files are ever read — written atomically via `tmpfile + os.replace`.

### 3. Forced re-run

`--rerun "phase=5,model=qwen3.6-35b,corpus=cuad"` flips matching rows back to `pending`. Selectors AND together. Useful when you change a question, change the rubric, or want to re-judge.

`--skip "model=deepseek-r1-8b"` flips matching rows to `skipped`. Useful when a model is known broken and you want to keep going.

## Failure handling

| Outcome | State | Phase 4 (completion-only) | Phase 5 (parity) |
| --- | --- | --- | --- |
| Model returns answer + citations | `done` | proceed | judge runs |
| Model returns no citations / empty answer | `degraded` | logged, sweep continues | judge runs anyway, marks "no-retrieval" |
| API error / timeout / OOM | `error` (3 retries with exponential backoff, then escalates) | sweep continues, model marked failed-on-corpus | sweep continues |
| Hard system error (DB down, llama-server crash, port unreachable) | `blocked` | sweep stops, prints diagnostics | sweep stops |

A `failed` model on one corpus does not abort other corpora — Phase 4 is "best effort across the matrix." A `blocked` system error does abort, since further work is meaningless without the system back up.

The retry policy: `tenacity` with exponential backoff at 1s, 5s, 15s. On the third failure, the row is marked `error` and we move on. The full traceback is recorded in `responses/<corpus>/<model>/<question_id>.error.json`.

A `blocked` system error (we detect it via 5xx repeated for >2 minutes, or `/api/system/health` returning unhealthy) prints diagnostics and exits non-zero. Resuming is a manual action.

## Bilingual scope

The synthetic corpus is the only bilingual corpus. The cross-language research question is a single shared question with two phrasings (`synthetic-research-6`):

```yaml
- id: synthetic-research-6
  variants:
    - lang: en
      text: "What were the major board decisions in Q3?"
    - lang: fr
      text: "Quelles étaient les principales décisions du conseil au troisième trimestre?"
```

Both phrasings run as separate completions. The harness then computes a **cross-language consistency** metric: `|sources_en ∩ sources_fr| / |sources_en ∪ sources_fr|`. Logged but not gating.

For the Claude baseline, the EN phrasing is the canonical one — the FR phrasing's completion is judged against the same EN baseline, since the test is "did the model find the same source docs regardless of language" rather than "did it produce identical prose." Cross-language consistency is reported separately from the parity score.

For the ask cross-language question (`synthetic-ask-10`), same pattern — two phrasings, two completions, one consistency metric.

## Out of Scope

- **Performance regression detection** — we don't compare this run to a previous run. Future work.
- **Multi-tenant testing** — Harbor Clerk is single-tenant by design; not relevant.
- **MCP-only sweep without LLM** — all tests go through the LLM, not the raw MCP tools.
- **Stress testing** — concurrent users, sustained load, etc. Future work.
- **Cost optimization of the synthetic generator** — Sonnet 4.6 is fine even at ~300 generations.
- **Long-term archival of run results** — `results/` is gitignored; user moves a run to `~/Library/Application Support/Harbor Clerk/test-corpora-archives/` if they want to keep it.

## Risks & mitigations

| Risk | Mitigation |
| --- | --- |
| A model crashes llama-server mid-run | Detected as `blocked`, sweep stops, user restarts llama-server, sweep resumes |
| Anthropic API rate limit during baseline generation | `tenacity` retries with backoff; if persistent, sweep marks baseline rows `error` and continues without them (Phase 5 skips affected questions) |
| CUAD download flaky | Retry, then fall back to mirror; document in README |
| Synthetic generator drifts in tone/format | Templated prompts with worked examples; spot-check after first 50 generations before completing the full set |
| Phase 4 takes longer than expected | All restart-safe; user can pause at any phase boundary |
| Disk fills with response JSONs | Each response file ~10–50 KB; full sweep < 100 MB. Acceptable. |

## Success criteria

The sweep is "complete and successful" when:

1. **Phase 0:** all three corpora ingested, `pipeline.queued + pipeline.running == 0`, doc_count matches expected per corpus ±5%.
2. **Phase 1:** all 48 baselines (one per logical question — cross-language pairs share the EN-canonical baseline) have `status == "done"` and a non-empty `answer` field.
3. **Phase 4:** every (model × corpus × question) cell has either `done`, `degraded`, `error`, `failed`, or `skipped` status. No `pending` or `blocked` left.
4. **Phase 5:** all 100 judge verdicts produced. Aggregate report shows median `claim_recall ≥ 4` for both top-2 models on each corpus. (Below that threshold: investigation, not failure — but flagged.)
5. **Phase 6:** unified-corpus subset completes. Cross-domain disambiguation report produced.
